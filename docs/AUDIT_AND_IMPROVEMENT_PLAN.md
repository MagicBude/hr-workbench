# 安全、质量与优化审查执行计划

> 审查日期：2026-08-11  
> 审查范围：`index.html`、`js/`、`tests/`、本地存储、导入导出及大表交互  
> 基线验证：`npm.cmd run verify` 通过；12 个 JavaScript 文件语法检查通过，9 项领域测试通过  
> 文档目的：统一归档已发现的问题，区分真实缺陷与误报，并提供可按批次执行的修复和验收清单。

---

## 1. 总体结论

项目模块边界清楚，已经具备花名册、考勤、薪资、看板、组织隔离、备份恢复和导出能力，适合作为纯前端、单设备使用的轻量工具或演示系统。

如果要保存真实员工和薪资数据，当前版本仍有四类主要风险：

1. **产品安全边界**：`localStorage` 无登录、权限、加密和审计，不适合多人共享或不受控设备。
2. **不可信数据边界**：导入验证较浅，部分 HTML 属性和 Excel/CSV 导出没有统一的安全处理。
3. **数据可靠性**：存储失败可能导致内存状态与磁盘状态不一致，用户可能误以为已经保存。
4. **规模与合规性**：大考勤表会随员工数线性膨胀；薪资和个税仍是演示口径，不能作为正式税务结果。

建议先完成 P0/P1，再考虑将工具用于真实内部数据。涉及账号、权限、多端同步和正式合规计算的事项，不能只靠前端局部修补完成。

## 2. 用户补充问题逐条核实

| # | 问题 | 核实结论 | 最终等级 | 说明 |
|---|---|---|---|---|
| 1 | 多处 `innerHTML` 导致 XSS | **部分成立** | P1 | 姓名、部门、节假日名称等主要文本已转义；`formatRestMinutes()` 只由数字生成固定文本，不是注入点。但导入数据未完整验证日期、ID、设置等字段，部分值进入 HTML 属性，因此仍应统一安全边界。纯本地场景利用门槛较高，不能笼统定为最高危。 |
| 2 | 使用原生 `prompt()` | **成立** | P2 | 会阻塞交互、样式不统一、无法做内联校验和无障碍处理；属于体验和维护问题，不是安全漏洞。 |
| 3 | 缺少错误边界和异常处理 | **成立** | P0 | `readJSON()` 静默回退，`writeJSON()` 未处理配额或禁用异常。修改内存后保存失败可能导致刷新后丢数据。 |
| 4 | 导入验证不完整 | **成立** | P0 | 员工 `id/name` 未要求必填；考勤、薪资、设置、日期、金额、引用关系、文件体积和数组长度未完整验证。 |
| 5 | 列宽持久化可能归零 | **条件成立，但当前不是稳定复现缺陷** | P3 | 当前花名册和考勤调用一般传入默认或已保存宽度；测量值为 0 时也有最小宽度兜底。隐藏表格或未来新增无默认宽度调用方时仍可能异常，适合防御性加固。 |
| 6 | 考勤逾期判断不准确 | **成立，原因需修正** | P1 | 空字符串本来会被判为未填；真实问题是只要 `am/pm/ot` 任意一个有值就把整天算作已填，会漏掉只填上午、下午空缺的情况。 |
| 7 | 调休余额可为负但无提示 | **部分成立** | P2 | 设置页已写明“关闭后允许调休余额为负数”，花名册也会显示负数；但具体操作完成后缺少醒目的透支提示、颜色和确认。 |
| 8 | 社保基数可为负数 | **成立** | P1 | 输入框有 `min=0`，但保存时没有检查 `validity`，并且导入数据也能写入负数。计算层直接使用该值。 |
| 9 | 大数据量渲染卡顿 | **成立** | P2 | 100 名员工的考勤表约生成 300 行、31 天三时段及汇总相关的大量单元格，重绘和事件绑定成本明显。应先基准测试，再分页或虚拟化。 |
| 10 | 列宽拖拽频繁操作 DOM | **部分成立** | P3 | 代码只修改同组列，不是无条件修改所有列；但 `mousemove` 每次同步写样式并可能重算 sticky 偏移，仍可用 `requestAnimationFrame` 合帧。 |
| 11 | 缺少统一日志/监控 | **成立，需按架构处理** | P2 | 纯离线工具不宜默认上传敏感 HR 数据。先做本地结构化错误日志和可导出的诊断信息；接入远程监控前必须脱敏、告知并获得授权。 |
| 12 | 快照无压缩 | **成立** | P1 | 每份快照复制整个组织数据，最多 10 份，很容易触及约数 MB 级的浏览器存储配额。压缩只能缓解，长期方案应是 IndexedDB 或后端存储。 |

## 3. P0：立即处理的数据安全与可靠性

### 3.1 建立可靠的持久化事务边界

**现状证据**

- `js/store.js:28-35`：读取异常被静默吞掉，写入直接调用 `localStorage.setItem()`。
- `js/store.js:123-125`：`persist()` 没有结果、错误分类或回滚能力。
- 业务模块通常先修改 `state.data`，再调用 `persist()`。

**风险**

- 存储被禁用、配额已满或 JSON 序列化失败时，界面可能仍保留修改后的内存数据。
- 用户继续操作或看到成功提示后，刷新页面才发现数据丢失。
- 读取到损坏 JSON 时直接使用空数据，可能让用户误以为原数据被清空。

**实施步骤**

- [ ] 定义 `StorageError`，区分不可用、配额不足、损坏数据和序列化失败。
- [ ] `writeJSON()` 返回明确结果或统一抛错，不再由调用方猜测。
- [ ] 修改业务操作为：生成候选数据 → 尝试持久化 → 成功后替换运行态；或失败时恢复变更前副本。
- [ ] `readJSON()` 遇到损坏数据时保留原始内容，显示恢复/导出入口，不自动当作空数据覆盖。
- [ ] 导入、清空、快照、恢复、员工编辑、考勤和薪资修改都显示真实保存结果。
- [ ] 增加 `QuotaExceededError`、损坏 JSON、禁止存储和序列化失败测试。

**验收标准**

- [ ] 模拟 `localStorage.setItem()` 抛错后，页面数据不会假装保存成功。
- [ ] 原存储数据仍可恢复，用户收到可操作的错误提示。
- [ ] 所有成功 Toast 只在持久化真正成功后出现。

### 3.2 完整的导入 Schema 与资源限制

**现状证据**

- `js/domain.js:122-146` 只验证部分顶层类型、员工文本类型、少量 ID 和重复员工 ID。
- `js/main.js:145-171` 在浏览器中直接读取并解析整个文件，没有文件大小限制。
- `org.id/org.name` 没有格式和长度校验。

**实施步骤**

- [ ] 备份根对象要求 `schemaVersion`、`org`、`data` 的明确结构。
- [ ] 员工要求非空且唯一的 `id`、非空 `name`，校验日期、状态、工资、调休和社保基数。
- [ ] 考勤校验 `month`、`empId`、日期键、`am/pm/ot`、状态枚举和分钟范围。
- [ ] 薪资校验金额为有限数、非负、状态合法，`comp/pers` 字段结构合法。
- [ ] 设置校验比例范围、半天分钟数、部门列表、节假日键和值。
- [ ] 校验所有 `empId` 引用均能找到员工；拒绝重复考勤和薪资业务键。
- [ ] 组织 ID 只允许安全字符并限制长度，组织名称限制长度和控制字符。
- [ ] 文件选择后先限制体积；解析后限制员工数、记录数、字符串长度和嵌套深度。
- [ ] 校验和迁移全部成功后再创建/切换组织及覆盖数据。

**验收标准**

- [ ] 缺少员工 ID/姓名、负金额、非法日期、未知考勤状态和孤立引用均被拒绝。
- [ ] 超大文件在解析或写入前被阻止，并给出明确原因。
- [ ] 任意导入失败都不会改变当前组织、组织列表或当前数据。

### 3.3 明确真实 HR 数据的使用边界

**现状**

所有员工、考勤和薪资数据以明文存放在同源 `localStorage`。系统没有登录、权限、会话锁定、审计或服务端控制。

**短期措施**

- [ ] README 和应用首次使用提示明确标注“单设备本地工具，不适合共享电脑和公开终端”。
- [ ] 提供一键锁定/清除会话展示功能，避免旁观者直接看到薪资。
- [ ] 不声称本地明文数据具备企业级安全性。

**正式生产方案（独立项目）**

- [ ] 后端认证、组织租户隔离和 RBAC。
- [ ] TLS、服务端加密、密钥管理、备份恢复和审计日志。
- [ ] 敏感字段访问审计、导出权限和最小权限设计。
- [ ] 数据保留与员工隐私合规策略。

## 4. P1：输入、导出与业务正确性

### 4.1 统一 DOM 输出安全策略

**核实说明**

- `escapeHtml()` 已覆盖姓名、部门、组织名和节假日名称的主要展示位置。
- `formatRestMinutes()` 只处理数值并返回“天/小时/分钟”固定文本，`emRestHint.innerHTML` 不是当前可利用的 XSS 点。
- 仍存在未统一处理的动态属性，例如员工 ID、导入日期、快照 ID，以及未来维护时新增字段遗漏转义的风险。

**实施步骤**

- [ ] 用户或导入数据优先通过 `textContent`、`value`、`dataset` 和 DOM API 写入。
- [ ] 必须使用模板 HTML 时，区分 `escapeHtml()` 与属性上下文处理，不把一个函数当作所有上下文的万能方案。
- [ ] ID、日期、月份和状态先做白名单验证，再进入属性或 class 名。
- [ ] `openModal(html)` 只接收内部可信模板；长期可改为接收 DOM 节点或组件构建函数。
- [ ] 增加恶意导入回归：HTML 标签、事件属性、引号、反引号、控制字符和异常 ID。
- [ ] 若部署环境允许，配置 CSP；由于当前存在内联样式，实施前先清理相应阻碍。

**验收标准**

- [ ] `<img src=x onerror=alert(1)>`、引号逃逸和恶意 ID 只作为普通文本或直接被导入校验拒绝。
- [ ] 自动测试覆盖文本节点、HTML 文本、属性值和 dataset 四类输出上下文。

### 4.2 修复 CSV/XLSX 公式注入和 CSV 格式

**现状证据**

- `js/payroll.js:187` 使用 `row.join(",")`，没有处理逗号、换行和双引号。
- 姓名、部门等用户文本可用 `= + - @` 开头，电子表格软件可能将其解释为公式。
- `js/export.js` 将用户文本直接交给 SheetJS，未显式执行危险公式前缀防护。

**实施步骤**

- [ ] 增加统一 `escapeCsvCell()`，遵循双引号转义和字段包裹规则。
- [ ] 对用户控制的文本执行公式前缀防护，并记录这一行为以免误解导出值。
- [ ] XLSX 导出确保用户文本单元格类型为字符串，不产生公式单元格。
- [ ] 增加包含逗号、双引号、换行、中文和公式前缀的导出测试。

**验收标准**

- [ ] Excel/LibreOffice 打开后列数、行数和原始文本保持正确。
- [ ] 公式前缀内容不会执行外部链接、命令或计算公式。

### 4.3 修复考勤待补录的半天漏报

**现状证据**

`js/main.js:51-54` 只要 `am`、`pm` 或 `ot` 任一字段非空，就将整天视为已填写。

**实施步骤**

- [ ] 按工作日分别检查上午和下午两个应出勤时段。
- [ ] 加班字段不得抵消上午或下午的缺失。
- [ ] 待办显示“缺少几个时段”或折算为缺失工时，而不是模糊的缺失天数。
- [ ] 复用 `attendanceMetrics()` 或新增统一领域函数，避免待办和看板采用不同口径。

**验收标准**

- [ ] 上午有值、下午为空时仍显示待补录。
- [ ] 仅填写加班时，上午和下午均计为未录入。
- [ ] 节假日、周末、入离职区间和当前日期边界正确。

### 4.4 阻止负社保基数和非法金额

**现状证据**

- `js/roster.js:296` 只有 HTML `min="0"`。
- `js/roster.js:325-326` 保存时直接转数字，没有检查输入有效性。
- `js/payroll.js:32-35` 直接使用员工社保基数。

**实施步骤**

- [ ] 保存前使用显式领域校验，不依赖 HTML 属性。
- [ ] 社保基数、基本工资、补贴、奖金、加班费和税额必须是有限数并符合业务范围。
- [ ] 导入与 UI 使用同一个校验函数。
- [ ] 计算函数对旧数据增加防御性规范化或阻断提示。

**验收标准**

- [ ] 负数、`Infinity`、指数异常值和非数字无法进入薪资计算。
- [ ] 旧数据存在非法值时明确提示修复，不静默生成错误工资。

### 4.5 快照容量治理

**现状证据**

`js/store.js:134-140` 每次将完整组织数据克隆进快照，并保留 10 份；快照与主数据共享有限的 `localStorage` 配额。

**实施步骤**

- [ ] 创建快照前估算写入后总容量并预警。
- [ ] 保存失败时自动保留主数据优先，不因快照失败阻止必要的安全导出。
- [ ] 提供删除单份/清理旧快照和导出快照功能。
- [ ] 短期可评估压缩，但需验证压缩库体积、恢复可靠性和损坏处理。
- [ ] 中期迁移到 IndexedDB；多端或多人场景迁移到后端，不以压缩代替架构升级。

**验收标准**

- [ ] 接近配额时用户在破坏性操作前收到明确提示。
- [ ] 快照写入失败不会造成主数据和当前操作的不可解释状态。

## 5. P2：交互、可观测性与规模优化

### 5.2 负调休余额的操作提醒

当前允许负余额是明确的组织设置，不应删除该能力，但需要增强可见性：

- [ ] 关闭强制校验时，在考勤状态选择区显示“允许透支”。
- [ ] 本次操作导致余额首次变负时二次确认或 Toast 警告。
- [ ] 花名册负余额使用警示色和“已透支”标签。
- [ ] 看板增加负余额人数或异常入口。

### 5.3 大考勤表性能

**实施顺序**

- [ ] 建立 100、300、1000 名员工的合成数据和性能基准。
- [ ] 记录首次渲染、月份切换、单格修改、批量操作和内存占用。
- [ ] 先实现分页/部门分片和局部行刷新，避免每次修改重绘整张表。
- [ ] 若 300+ 员工仍不达标，再实施纵向虚拟滚动；横向日期列虚拟化需谨慎处理 sticky 列和拖选。

**建议性能目标**

- 100 名员工首次渲染不超过 500ms。
- 单格修改到视觉反馈不超过 100ms。
- 月份切换期间有明确加载状态，不冻结页面交互。

### 5.4 本地错误日志与隐私友好的诊断

- [ ] 增加统一 `reportError(error, context)`，记录时间、模块、操作类型、错误类别和应用版本。
- [ ] 不记录姓名、薪资、考勤明细、完整导入内容或 localStorage 原文。
- [ ] 设置中心提供“导出诊断信息”，由用户主动发送。
- [ ] 捕获 `error` 和 `unhandledrejection`，但避免重复记录已处理错误。
- [ ] 远程监控作为独立、显式启用功能；必须脱敏、告知用途并提供关闭方式。

## 6. P3：防御性加固与微优化

### 6.1 列宽测量防御

当前并无证据表明列宽会稳定归零，但可以低成本加固：

- [ ] 表格隐藏或 `getBoundingClientRect().width <= 0` 时延迟到可见后测量。
- [ ] 所有调用方都提供完整默认宽度。
- [ ] 保存前验证数组长度、有限数和最小/最大宽度。
- [ ] 损坏的列宽偏好自动丢弃并恢复默认值。

### 6.2 拖拽列宽合帧

- [ ] 用 `requestAnimationFrame` 合并同一帧内的 `mousemove`。
- [ ] 只修改目标组的 `<col>`，避免无关列循环。
- [ ] sticky 偏移只在固定列组变化时重算。
- [ ] 在低性能设备和考勤大表上对比优化前后的帧率，再决定是否保留复杂度。

### 6.3 ID 生成

`Date.now()` 在快速连续操作、自动化或数据合并时可能碰撞。

- [ ] 新员工、组织和快照 ID 改用 `crypto.randomUUID()`。
- [ ] 为不支持该 API 的旧环境提供随机回退。
- [ ] 导入时继续执行唯一性和业务键冲突校验。

## 7. 薪资合规与计算边界

当前个税使用固定起征点和单一演示税率，社保比例也是简化配置；未覆盖累计预扣、税率级距、专项附加扣除、社保上下限和月中入离职工资折算。

- [ ] 页面和导出文件显著标记“演示估算，不构成正式薪资/税务结果”。
- [ ] 若要正式使用，建立按地区和生效日期版本化的规则引擎。
- [ ] 每条已确认薪资保存计算规则版本和输入快照，确保可追溯。
- [ ] 补充舍入、累计税额、跨年、补发、负向调整和月中入离职测试。
- [ ] 正式规则上线前由财税专业人员复核。

## 9. 推荐实施批次

| 批次 | 优先级 | 工作内容 | 完成标志 |
|---|---|---|---|
| A | P0 | 存储错误处理、事务式保存、损坏数据恢复 | 保存失败不再静默，状态可回滚 |
