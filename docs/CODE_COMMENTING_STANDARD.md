# 教材型代码与注释规范

> 适用范围：本项目全部自有 HTML、CSS、JavaScript、测试和维护脚本。  
> 核心原则：源码既要正确运行，也要帮助学习者理解浏览器、状态、业务规则与工程取舍。

---

## 1. 质量目标

注释质量不按数量判断，而按以下问题能否从源码中得到答案判断：

1. 这个文件和函数为什么存在？
2. 数据从哪里来，经过什么变化，最后到哪里？
3. 为什么采用当前实现，而不是更直观的另一种写法？
4. 哪些业务规则、浏览器限制或安全边界不能被随意改变？
5. 修改这里会影响哪些页面、数据和测试？
6. 出错时会发生什么，调用方需要承担什么责任？

不追求“每行都有注释”。代码本身可以清楚表达的内容，应通过命名和结构表达。

---

## 2. 文件头规范

每个自有源码文件必须在顶部说明：

- 文件职责。
- 主要输入和输出。
- 与哪些模块或页面协作。
- 关键加载顺序或运行环境。
- 修改时最容易破坏的约束。

JavaScript 示例：

```js
/*
 * domain.js — 可脱离浏览器运行的业务规则
 *
 * 输入：员工、考勤、薪资和导入数据等普通对象。
 * 输出：统计结果、薪资记录或校验错误；本文件不读写 DOM/localStorage。
 * 协作：页面模块调用这里的规则，tests/domain.test.js 直接测试同一实现。
 * 约束：业务口径必须在这里保持单一来源，不能在看板和导出模块各写一份。
 */
```

文件头不需要罗列文件里的每一个函数，但必须让第一次打开文件的人知道它在架构中的位置。

## 3. `#region` 分区规范

使用编辑器可折叠区域，而不是只画分隔线。

```js
// #region 常量与运行状态
// #endregion
```

```css
/* #region 设计令牌 */
/* #endregion */
```

```html
<!-- #region 顶部组织与数据操作 -->
<!-- #endregion -->
```

分区原则：

- 按职责划分，不按“第 1 段、第 2 段”划分。
- 标题使用短中文，例如“导入导出”“薪资计算”“表格渲染”。
- 一个区域应包含一组能一起理解的代码。
- 通常一个文件使用 3–10 个区域；不要为每个小函数建立区域。
- 新增逻辑时放入正确区域，避免所有代码继续堆在文件末尾。

## 4. 应该写什么注释

### 4.1 解释业务口径

```js
// 离职当天仍属于任职区间，因此只在 date > leaveDate 时排除员工。
```

```js
// 迟到和早退属于异常次数，但员工仍完成了该时段出勤，不能扣掉整个半天工时。
```

业务注释应说明包含关系、边界日期、单位、舍入方式和历史数据兼容方式。

### 4.2 解释技术选择

```js
// 使用中午时间构造本地 Date，避免午夜在部分时区换算时落到前一天。
```

```css
/* 16px 可避免 iOS Safari 在输入框聚焦时自动放大页面。 */
```

### 4.3 解释副作用和协作关系

```js
// 修改组织设置后，考勤、薪资和看板都会读取新规则，因此需要刷新这些视图。
```

### 4.4 解释安全与恢复边界

```js
// 先校验完整导入包，再切换组织；否则校验失败也会改变当前组织选择。
```

### 4.5 解释非显而易见的性能处理

```js
// mousemove 可能在一帧内触发多次，用 requestAnimationFrame 合并 DOM 写入以减少布局抖动。
```

## 5. 不应该写什么注释

避免复述代码：

```js
// 错误：设置姓名
employee.name = name;
```

避免阶段性历史：

```js
// 错误：这次修复了上次的 bug
```

避免不确定承诺：

```js
// 错误：以后这里接后端就行
```

如果未来扩展确实影响当前设计，应写清边界：

```js
// 当前接口是同步的 localStorage 仓库；迁移异步后端时，调用链必须整体改为可等待操作，
// 不能只把 writeJSON() 替换成 fetch()。
```

避免保留失效注释。实现、字段名或业务规则变化时，注释和文档必须同时更新。

## 6. 函数与变量可读性

### 6.1 函数说明

以下函数需要说明输入、输出或边界：

- 业务计算函数。
- 数据迁移和校验函数。
- 有存储、下载、弹窗或全局状态副作用的函数。
- 坐标、日期、金额和比例换算函数。
- 超过约 25 行或包含多个分支的函数。

简单 getter 或命名已经完全表达行为的函数，无需机械补充注释。

### 6.2 变量命名

短变量只适合非常小的局部作用域：

- 循环索引可用 `i`。
- 数学坐标可用 `x/y`。
- 数组回调的一行表达式可用 `employee => ...`，不要用含义不明的 `e => ...`。

跨越多行时优先使用：

- `employee`，不要使用 `e`。
- `payrollRecord`，不要使用 `p`。
- `attendanceRecord`，不要使用 `a`。
- `settings`，不要使用 `st`。
- `tableBody/tableFoot`，不要使用 `tb/tf`。
- `companyContributions/personalContributions`，不要使用 `comp/pers`。

### 6.3 格式

- 一个独立操作占一行。
- 多分支逻辑使用花括号和缩进，不把完整函数压成一行。
- 长模板、长参数列表和长刷新列表应合理换行。
- CSS 组件规则通常展开为一条属性一行；极短工具类允许单行。
- 格式调整不得顺便改变业务逻辑。
- 提交前运行 `npm.cmd run format`，使用仓库固定的 Prettier 版本统一排版；
  不要依靠个人编辑器设置产生另一套格式。

## 7. 各语言专项要求

### 7.1 HTML

- 文件头说明页面用途、脚本加载方式和动态容器由谁填充。
- 用 `#region` 标记顶部栏、待办、导航、各业务区、公共弹窗和脚本。
- 关键 `data-*`、ARIA、隐藏文件输入和脚本顺序解释原因。
- 不给显而易见的普通容器逐个添加“这是一个 div”式注释。

### 7.2 CSS

- 文件头说明设计令牌、响应式策略和对应 HTML/JS 状态类。
- 用 `#region` 标记令牌、基础样式、组件、各业务模块、响应式和打印等区域。
- 解释 Flex/Grid 选择、sticky 层级、移动端断点、触控尺寸和浏览器兼容处理。
- 颜色和尺寸的说明应表达语义，不只是重复十六进制值。

### 7.3 JavaScript

- 文件头说明数据流和模块协作。
- 复杂函数说明业务规则、输入输出和副作用。
- DOM 渲染、事件绑定、存储和领域计算分区。
- 不可信输入进入 HTML、属性、文件或存储时说明安全策略。
- 金额、日期、分钟、比例等单位必须在命名或注释中明确。

### 7.4 测试

- 文件头说明测试对象、运行环境和未覆盖的浏览器边界。
- 测试名称应直接表达业务情景与期望结果。
- 对不直观的测试数据解释为什么选择该边界。
- 不为普通 `assert.equal()` 逐行写注释。

## 8. 本项目重点口径

维护以下逻辑时必须保留或补充解释：

- 员工入职、离职、停薪和回收状态对日期/月度有效性的影响。
- 工作日、周末、法定节假日和调休上班日的覆盖顺序。
- 上午/下午的标准分钟数及部分请假、缺勤的拆分方式。
- 迟到/早退为何计异常但仍计出勤。
- 加班转调休比例、默认加班时长和负余额开关。
- 薪资草稿、已确认、已发放记录为什么采用不同重算策略。
- 个税和社保为什么只是演示估算，以及正式合规能力的边界。
- 导入为什么必须先校验、再迁移、最后覆盖。
- 快照、清空和恢复操作的数据安全顺序。

## 9. 审查清单

提交前逐项检查：

- [ ] 新文件有完整文件头。
- [ ] 复杂文件有可折叠 `#region`。
- [ ] 注释解释原因、口径或边界，而不是复述代码。
- [ ] 没有过期字段名、错误承诺或补丁历史注释。
- [ ] 变量名能让学习者不回看定义也理解含义。
- [ ] 复杂逻辑可以逐行断点调试，没有过度压缩。
- [ ] 安全、存储、兼容性和性能取舍有说明。
- [ ] 实现变化已同步测试和相关文档。
- [ ] `npm.cmd run verify` 通过。

## 10. 与安全治理文档的关系

本规范回答“代码应该怎样写、怎样解释”。具体漏洞、优先级、修复步骤和验收标准记录在 `AUDIT_AND_IMPROVEMENT_PLAN.md`。治理安全问题时两份文档必须同时遵守：既要修复行为，也要把安全边界解释清楚。
